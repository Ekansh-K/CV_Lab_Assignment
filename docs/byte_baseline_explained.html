1. What problem BASE-0 solves

Multi-Object Tracking (MOT): given video frames, output trajectories — frame, id, x, y, w, h per person, with stable IDs through occlusion, crossings, camera shake.

Three families

  • Tracking-by-detection (this base): strong detector + lightweight associator. Wins on crowded linear MOT17/MOT20. Example: SORT → DeepSORT → ByteTrack → OC-SORT → Hybrid-SORT.
  • Joint detection+embedding (JDE): one net outputs boxes + ReID vector (FairMOT, YOLO11-JDE). Good when clothes differ.
  • End-to-end query trackers: Transformer propagates queries (MOTR, MOTRv2). Wins on dance/sports non-linear motion, needs 8 GPUs.

Why ByteTrack was the 2022 inflection

  • Before: throw away boxes with score < 0.5–0.6. Occluded people vanish → FN + ID switches.
  • ByteTrack insight: low-score boxes are usually occluded true positives, not background. Match them in a second round with motion only.
  • Result MOT17 test: 80.3 MOTA / 77.3 IDF1 / 63.1 HOTA @ ~30 FPS V100. Ablation (CrowdHuman+MOT17-half-train → half-val): 76.6 MOTA / 79.3 IDF1 / 159 IDSW. DanceTrack test: 47.7 HOTA / 89.6 MOTA — MOTA stays high while association collapses. That split is exactly why HOTA matters.

Your SYNTHESIS.md (§Stage A) stresses: MOTA ≈ 1−Σ(FN+FP+IDSW)/ΣGT is detector-heavy (R² 0.96 with DetA, 0.46 with AssA). HOTA = √(DetA·AssA) averaged over localisation thresholds is the balanced score. Lead with HOTA.

3. Detector: YOLOX-X in detail

ByteTrack does not invent a detector. It uses YOLOX (Ge et al. 2021), the YOLOv3-SPP baseline upgraded:

In this lab: you download only — pretrained/bytetrack_dance_model.pth.tar (YOLOX-X trained on DanceTrack by ByteTrack/Hybrid-SORT zoo). No X-training (that is 80 epochs, batch 48, 8×V100, MOT17+CrowdHuman+CityPersons+ETHZ). Inference: -b 1 -d 1 --fp16 --fuse, image 800×1440. Both BYTE and Hybrid-SORT share this exact checkpoint — detector frozen, so MOTA barely moves (88.3→89.5) and all HOTA gain is association.

4. Motion model: Kalman filter

Each track holds a constant-velocity Kalman state (SORT convention):

state x = [cx, cy, aspect a=w/h, height h, vx, vy, va, vh]^T   (8-dim)
measure z = [cx, cy, a, h]  from detector box
F = [[I4, I4],[0, I4]]  (position += velocity),  H = [I4, 0]
Predict: x' = F·x,  P' = F·P·Fᵀ + Q
Update:  K = P'·Hᵀ(H·P'·Hᵀ+R)⁻¹,  x = x'+K(z−H·x'),  P = (I−K·H)P'

Q/R tuned with high initial velocity uncertainty (P[4:,4:] *= 1000 style). If a track misses, it still predicts forward up to max_age=30 frames so reappearance can re-match. No camera-motion compensation, no appearance — pure linear prediction + IoU overlap. Cheap, but fails under dance spins / handheld shake (hence OC-SORT/Hybrid fix later).

5. Core invention: BYTE association

The bug it fixes

SORT/DeepSORT: if score < τ_high: discard. Under occlusion detector still fires but with score 0.2–0.4 → discarded → track dies → new ID on reappearance (IDSW + fragmentation).

BYTE two-round matching (per frame)

inputs: detections D (with scores), tracks T (Kalman-predicted boxes)
1. split: D_high = {s ≥ τ_high (0.5/0.6)}, D_low = {0.1 < s < τ_high}
2. ROUND 1: cost = 1 − IoU(D_high, predict(T))
   Hungarian assign (reject < iou_thresh 0.3). Matched → update Kalman.
   → unmatched tracks Tu, unmatched dets Du
3. ROUND 2 (BYTE): cost = 1 − IoU(D_low, predict(Tu))
   Hungarian assign. Matched → update (recovers occluded).
   → still-unmatched tracks stay Lost.
4. Birth: Du with s ≥ τ_high → new track (needs min_hits=3 to confirm).
5. Kill: Lost > max_age (30) → Removed.

Key properties: Round 2 never creates new tracks (low boxes only rescue existing tracks → few FP). No ReID cosine, no GIoU — vanilla IoU + Hungarian (lap / scipy.linear_sum_assignment). Second match is why IDSW 1947 here vs SORT's much higher, and why MOTA jumps on MOT17 (fewer FN).

6. Tracklet lifecycle

New (tentative, <3 hits) → Tracked (active) ⇄ Lost (no match, ≤30 frames, Kalman coasts) → Removed (>30)
Confirmed only if hit_streak ≥ min_hits (3) or frame_count ≤ 3. MOT output only for time_since_update < 1 (currently visible). Interpolation + per-sequence threshold tuning used only for test-server submission, not val here.

7. Pseudocode + thresholds used here

BYTETracker(args, frame_rate=30):
  track_thresh = 0.5-0.6   # τ_high (exp yolox_dancetrack_val.py)
  low_thresh   = 0.1       # τ_low
  iou_thresh   = 0.3
  max_age = 30  (~1 sec), min_hits = 3
  det_thresh alias = track_thresh in HybridSORT wrapper

def update(dets):
  dets_high, dets_low = split(dets)
  preds = [kalman.predict() for t in tracks]
  m1, uD, uT = hungarian(iou(dets_high, preds))
  for (d,t) in m1: tracks[t].update(dets_high[d])
  m2, _, uT2 = hungarian(iou(dets_low, preds[uT]))
  for (d,t) in m2: tracks[t].update(dets_low[d])  # rescue
  for t in uT2: tracks[t].mark_lost(); predict coasting
  for d in uD: if score≥track_thresh: birth(d)
  retire Lost>30; output Tracked

DanceTrack = uniform appearance + diverse non-linear motion. Oracle-IoU is 98.1 HOTA on MOT17 val but only 72.8 on DanceTrack; appearance can even hurt (SYNTHESIS §Stage B). So BYTE's linear Kalman + IoU collapses on AssA while DetA/MOTA stay high. Published anchors: ByteTrack val 47.1 / test 47.3–47.7; your 47.124 is a near-exact repro — required gate before claiming any upgrade.

9. Failure modes → why Hybrid-SORT is needed (preview of UPGRADE-1)

  • Kalman linear error during occlusion/spin: prediction drifts, IoU→0, track lost. Fix: Hybrid's TCM (confidence-modelled Kalman, 9-dim with score), observation-centric re-update, 4-corner velocity.
  • IoU too weak for fast deformation: Fix: Height_Modulated_IoU + direction consistency (inertia 0.2, delta_t 3).
  • Camera motion: Fix (BoT-SORT style CMC) — out of BYTE scope.
  • Result: same YOLOX boxes, HOTA 47.124→59.570 (+12.4), AssA 31.56→45.14, IDSW 1947→1701. MOTA only 88.3→89.5 because detector frozen — proof gain is association.

Do not compare 47.1/59.6 to MOT17 80.3 MOTA — different dataset + test-server + interpolation protocol. Allowed sentence is in docs/report-notes.md.
